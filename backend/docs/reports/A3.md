## The executor (arch 6.4), in the order the rules apply

1. **Whitelist:** only a name in the registry runs (a dict lookup, never `getattr`). Anything else → `unknown_tool`. A spec without a handler is logged and left out. Today all 41 of A2's tools have a handler (tested).
2. **Proactive runs are read-only (D22):** only `get_*`, `simulate_plan`, `suggest_savings_products`, `show_quick_replies` and `mark_event_handled` run. Any other tool → `not_allowed_in_proactive`. The check uses names, not A2's flags, so it still holds if `tools_for` breaks.
3. **`user_id`** comes only from `ctx`. An input that contains `user_id` is refused.
4. **Pydantic validation** with A2's input model → `invalid_input`, which names the fields and the reasons and never echoes the values. A2 found that the API accepts at most 20 strict tools per request, so this validation is the real guard.
5. `DomainError` → `is_error` with its code. Any other exception → a generic `internal_error`, logged with its traceback. The loop continues.
6. **D18:** after a successful money tool, `recompute_plan(db, user_id, reason, trigger_ref)` and then `forecast_goal(db, user_id, plan.version)` run. The result gets `plan` + `forecast`, both with their previous values. `trigger_ref` = `{tool, tool_use_id, …ids from the handler}`. A handler can set `_plan_reason` (e.g. `annotation: tx 918 500.00 → 100.00`).
7. **Every call is logged** through `tool_calls.log` (`ok` / `error`). A failing log never breaks the call.

Content is always JSON: `{"ok": true, …}` or `{"ok": false, "error": {"code", "message"}}` with `is_error: true`.

## `apply_annotation` (keeps S0's signature; shared with B6's `PATCH /transactions`)

- Effective amount = `own_amount` if given (it wins; it must be within 0..amount, else `invalid_own_amount`).
- Else `split_share(amount, people_count)`.
- Else, for a shared purchase (others repay, beneficiary `shared`/`others`, or purpose `on_behalf_of_others`): `own_share_estimate`, with `estimated: true` and the result clamped to 0..amount.
- Else (for the user alone): the whole amount.

When the others will repay and their share is > 0, a receivable is created: `expected_by` = today + 14, and `amount_each` = others / (people_count − 1). An open receivable that no longer matches is **cancelled** (a correction); the same answer twice keeps the one it has. After that come `on_annotation_changed(old, new)`, `learn_from_annotation`, and the open question is marked `answered`. The result is `AnnotationResult`, whose S0 fields are kept, plus `amount`, `previous_effective_amount`, `receivable_id`, `people_count`, `cancelled_receivable_id` and `answered_event_id`.

Tested: 5 people → 100 + 400 (100 each); `own_amount` 120 → 120 + 380 (95 each); `own_amount` 500.01 or −1 → error; 1 person → no receivable; no count and no amount → estimated, clamped; a correction → receivable cancelled + ledger delta 100 → 500; another user's transaction → `not_found`; the question marked answered. Scene A goes through the executor: plan + forecast (77% vs 71%), then `offer_payment_request` → the card "Trimite cererea (4 × 100 lei)", status still `open`; on a paid receivable → `receivable_not_open`.

## Other handlers (decisions)

- `add_life_fact` / `update_life_fact`: the value is validated with F2's `LifeFactDraft` (`invalid_fact`). Then `signatures_for_fact` (with Claude's `signatures`), `signatures.replace_for_fact`, `on_fact_changed`. `expire_life_fact` / a rejected hypothesis replace the signatures with `[]`.
- `create_pattern_rule`: F2's `PatternRule`, `source = explicit`, confidence 0.9 (C8's rule for an explicit recurrence).
- `set_goal` with an active goal → `goal_already_active`. `update_goal` without one → `no_active_goal`. A deadline that isn't in the future → `invalid_deadline`.
- `complete_onboarding` → `onboarding_incomplete`, "Still missing: …" from `goal`, `income`, `fixed_costs`, `life_context` (= at least one confirmed, active life fact).
- `shape_budget` merges A2's list shapes (ISO weekdays, `pin_days`, caps where null removes a cap) into F2's `PlanPreferences`. `record_slip_reason` with `recurring` adds +0.25 to that weekday's weight (capped at 3).
- `update_life_profile` refuses a key that is a `FactType` (→ `use_add_life_fact`).
- The reads write nothing. `simulate_plan` returns `saved: false`. `suggest_savings_products` ranks by the goal horizon, then by rate, with a one-line reason each (a first cut of C12).
- `show_quick_replies` sets `run.quick_replies` (1–5, deduplicated). WebSocket events go into `run.pushes`, for A6/bomboe to push after the commit.
